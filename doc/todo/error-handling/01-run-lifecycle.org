Make ~LoxVisualizer~ survive an exception out of ~runSource~.  TypeScript only;
no C changes and no dependency on the Errors pane work in ~design.org~.

* Background

~lox.exports.runSource(text)~ is a synchronous ~cwrap~ call with no ~try~ at
either call site — ~setUp()~ and ~rerun()~.  Everything after the call in that
function is skipped when it throws, and today it throws on *any* Lox compile or
runtime error, not just a crash (see ~crash-resilience.org~).

What gets skipped:

- ~delete this.root.dataset.running~ → Build button stuck disabled forever
  (~[data-running] .lox-run-button~ sets ~pointer-events: none~)
- ~executionStore.set({steps, prints, currentStep})~ → stack / playback /
  bytecode-arrow panels blank, though ~this.stepBuffer~ holds the trace
- the MAX_STEPS cap warning
- in ~setUp()~ only: ~observeViewport~, ~visualViewport~ keyboard handling, touch
  swipe handlers, ~resize~/~scroll~ connector refresh, ~documentClickHandler~

Note the two call sites currently duplicate the ~dataset.running~ /
~executionStore.set~ / MAX_STEPS blocks verbatim.  Extracting the helper removes
that duplication as a side effect.

** DONE Extract ~runAndPublish~ helper
   :PROPERTIES:

One private method owning the whole run lifecycle: set the running flag, call
the module, publish results no matter what.

#+begin_src typescript
  private runAndPublish(text: string): void {
      this.root.dataset.running = '';
      try {
          this.lox.exports.runSource(text);
      } catch (e) {
          this.reportRunFailure(e);
      } finally {
          delete this.root.dataset.running;
          this.executionStore.set({
              steps: this.stepBuffer,
              prints: this.printBuffer,
              currentStep: this.stepBuffer.length > 0 ? 0 : null,
          });
          if (this.stepBuffer.length >= MAX_STEPS) {
              this.loxState.push('consoleMessages', {
                  type: 'error',
                  text: `Execution trace capped at ${MAX_STEPS.toLocaleString()} steps — program may have an infinite loop.`,
              });
              this.publishConsole();
          }
          // The run may have died before lexer EOF / parser PROGRAM_CLOSE, so
          // the rAF render was never scheduled. Guarantee one render.
          if (!this.rendered) {
              this.rendered = true;
              this.render();
          }
      }
  }
#+end_src

Then delete the duplicated blocks from ~setUp()~ and ~rerun()~; both call
~this.runAndPublish(text)~.

Keep ~publishConsole()~ inside the ~finally~ — the stderr handler publishes
incrementally during the run, but the cap message is appended after it.

#+begin_src typescript
  private reportRunFailure(e: unknown): void {
      const detail = e instanceof Error ? e.message : String(e);
      console.error('lox-visualizer: run failed', e);
      this.loxState.push('consoleMessages', { type: 'error', text: `Interpreter stopped: ${detail}` });
      this.publishConsole();
  }
#+end_src

~ExitStatus~ is not an ~Error~ subclass in the Emscripten glue, so the
~String(e)~ branch matters — do not assume ~e.message~ exists.

Deviations from the plan above, and why:

** ~describeThrown~ helper instead of an inline ~String(e)~

The sketch's ~e instanceof Error ? e.message : String(e)~ is wrong for the case
it was written for.  Emscripten's ~ExitStatus~ is a plain class carrying
~message~ and ~status~ — not an ~Error~ — so ~String(e)~ yields
~"[object Object]"~ and the reader learns nothing.  ~describeThrown~ reads
~message~ off any object that has one, falling back to ~String~.  There is a
test pinning this.

** Bootstrap extracted to ~main.ts~

Taken up as in the note under "Unit tests": the orchestrator self-instantiated
on import, so *any* test importing it mounted a visualizer as a side effect.
~lox-visualizer.ts~ now exports ~LoxVisualizer~ and is side-effect free; the
bootstrap lives in ~app/src/lox-visualizer/main.ts~.

The Vite input *key* still reads ~lox-visualizer/lox-visualizer~, so the built
file and the URL in posts (~/app/lox-visualizer/lox-visualizer.js~) are
unchanged — only the source path behind it moved.  Verified with a one-shot
build: the entry contains the class and the bootstrap.

~python-visualizer.ts~ has the same self-mounting shape and was left alone.
Worth the same treatment when it next needs tests.

** ~tsconfig.test.json~ created

~make typecheck~ referenced it, but it was never committed — the target failed
for everyone with ~TS5058: The specified path does not exist~.  It now extends
the app config with ~types: ["vitest/globals"]~ and ~exclude: []~.  ~exclude~
must be cleared rather than the include narrowed to ~*.test.ts~, or ambient
declarations (~app/src/types/pyodide.d.ts~, which declares ~*.py?raw~) fall out
of the test project and ~py-core.ts~ fails to resolve its emitter import.

** Tests mount a layout without the AST panel

~drawAst~ drives d3-zoom, which reads SVG geometry (~width.baseVal~) that jsdom
does not implement, and it reads ~prefers-reduced-motion~ via ~matchMedia~,
which jsdom also lacks.  ~fromPage~ already accepts a layout, so the tests pass
~[['editor','lexer'],['bytecode','console']]~ rather than shimming the SVG DOM.
~ResizeObserver~ and ~matchMedia~ still need stubbing for ~observeViewport~.

Note this means the forced-render path is exercised without the AST panel
attached.  If that panel ever gets its own jsdom shim, widen the test layout.
