** DONE Step-count cap with a warning
   :PROPERTIES:
   :files:    app/src/lox-visualizer/lox-visualizer-demo.ts (or orchestrator), 01-c-event.org follow-up
   :END:

For programs with long loops, the step array can become very large.  Add a
frontend cap:

#+begin_src typescript
const MAX_STEPS = 10_000;

events.on('vm_step', (event: VmStep) => {
    const current = this.executionStore.get();
    if (current.steps.length >= MAX_STEPS) return;
    this.executionStore.set({ steps: [...current.steps, event] });
});
#+end_src

After =runSource= returns, if =steps.length >= MAX_STEPS=, show a banner:

#+begin_src typescript
if (steps.length >= MAX_STEPS) {
    console.warn(`Execution trace capped at ${MAX_STEPS} steps.`);
    // optionally show a UI notice in the console panel
}
#+end_src

A C-side cap (emitting a special sentinel event when the limit is hit) is
cleaner but optional — the frontend cap is sufficient for now.

** DONE Optimize store push for large traces
   :PROPERTIES:
   :files:    app/src/lox-visualizer/lox-visualizer-demo.ts
   :END:

The spread-copy in the =vm_step= handler (=steps: [...current.steps, event]=)
allocates a new array on every step.  For large traces this is O(n²) total
allocation.

Replace with a mutable module-level array that the store holds by reference:

#+begin_src typescript
// Outside the class / in setUp:
const stepBuffer: VmStep[] = [];

events.on('vm_step', (event: VmStep) => {
    if (stepBuffer.length >= MAX_STEPS) return;
    stepBuffer.push(event);
    // Notify subscribers by writing the same reference with a version bump,
    // or use a wrapper object { steps, version } so subscribers see a change.
});

// After runSource:
this.executionStore.set({ currentStep: stepBuffer.length > 0 ? 0 : null });
#+end_src

This requires the store's change-detection to see a change even when the array
reference doesn't change.  One option: wrap steps as ={ steps: VmStep[];
version: number }= and increment =version= on each push; subscribers read =steps=.
