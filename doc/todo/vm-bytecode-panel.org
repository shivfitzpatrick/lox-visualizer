#+title: VM Bytecode Panel
#+date: 2026-06-17

Display a panel below the AST that lists the VM instructions output by the
clox compiler.  Instructions are emitted as JSON after compilation completes
and rendered in the frontend as a collapsible, hoverable list.

Chosen design:
- *Chunks*: all chunks (script + all nested function/closure/method chunks)
- *Emit strategy*: batch after ~compile()~ returns, with source character
  offsets stored in a parallel array on ~Chunk~
- *Interactivity*: hovering an instruction highlights the matching source
  span and AST node (linked via ~src_offset~ ↔ ~AstNode.start~)

* Background

clox emits JSON events to stdout via ~printf~ guarded by compile-time flags
(~JSON_LOG_SCANNER~, ~JSON_LOG_AST~).  Emscripten captures stdout and the
frontend dispatches events by ~msg_type~.

The compiler produces one ~Chunk~ per function/closure/method.  The top-level
script is the ~ObjFunction~ returned by ~compile()~; inner functions are stored
as ~OBJ_FUNCTION~ constants within their enclosing chunk's ~ValueArray~.

~Chunk~ currently stores line numbers via a run-length-encoded ~LineArray~ but
does not store source character offsets.  AST nodes carry ~start~ (source char
offset) via the parser event pipeline.  To link instructions to AST nodes we
need the same ~start~ values recorded at instruction-emit time.

Add a new function ~disassembleChunkJSON~ that walks a ~Chunk~ and emits one
JSON line per logical instruction (not per byte).  Each line must include:

#+begin_src json
{"msg_type": "compiler", "chunk": "<name>", "offset": 0,
 "op": "OP_CONSTANT", "line": 1, "src_offset": 4,

Fields:
- ~chunk~: function name (use ~"<script>"~ for the top-level chunk)

  (model after the existing ~constantInstruction~, ~byteInstruction~,
  ~jumpInstruction~ helpers — add JSON-emitting variants)

After emitting all instructions in a chunk, recursively walk
~chunk->constants~ looking for ~OBJ_FUNCTION~ values and call
~disassembleChunkJSON~ on each, using the function's name as the chunk label.

Declare in ~debug.h~:

Initialize to ~[]~ in the constructor.  Add a ~compile()~ method that groups

order = natural chunk order: script first, then nested functions as they
appear in the constants).

#+begin_src typescript
compile(): Map<string, CompilerEvent[]> {
  const chunks = new Map<string, CompilerEvent[]>();
  for (const event of this.get('compilerEvents')) {
    let list = chunks.get(event.chunk);
    if (!list) { list = []; chunks.set(event.chunk, list); }
    list.push(event);
  }
  return chunks;
}
#+end_src

* Open questions

- *Completion signal*: piggy-backing on ~parserRendered~ assumes compiler
  events arrive before the parser CLOSE event — test this assumption and
  adjust if needed.  A cleaner option: emit a ~{"msg_type": "compiler",
  "action": "done"}~ sentinel from ~vm.c~ after the recursive walk.
- *Jump operand display*: jumps emit a target offset (~jump_target~).  Should
  we render jump targets as clickable links that scroll to the target row?
- *Closure upvalue lines*: ~OP_CLOSURE~ is followed by upvalue descriptor
  bytes that the existing disassembler prints separately.  Decide whether
  to show these as sub-rows or fold them into the ~OP_CLOSURE~ row.
- *AST highlight API*: the connector feature (~ast-token-connector.org~)
  adds an ~onHighlight~ callback to ~drawAst~.  If that task is complete,
  the bytecode panel can reuse it directly.  If not, we need a lighter-weight
  mechanism (e.g., a shared observable or a direct d3 selection query).
