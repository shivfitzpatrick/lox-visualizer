#+title: Fix Instruction → AST Node Connector (src_offset anchoring)
#+date: 2026-06-18

Make the bytecode panel connect each VM instruction to the AST node that
actually produced it.  Today the connector keys on ~CompilerEvent.src_offset~
== ~AstNode.start~, but the compiler stamps instructions with the wrong source
offset, so the line drawn between the bytecode row and the AST node lands on
the wrong node (or nowhere).

* Background

** How the connection works
The visualizer joins an instruction to a node purely by source byte offset:

- Every AST node carries a ~start~ (its source offset), set in
  ~state/state.ts~ via ~createNode(..., start)~ / ~expressionNode(type, start,
  ...)~, and rendered as ~data-start~ on the SVG ~g~ in ~ast.ts~.
- ~onInstructionClick~ (~lox-visualizer-demo.ts~) looks up
  ~#lox-ast g[data-start="${instr.src_offset}"]~ and only draws the
  ~bc-ast~ connector when ~instr.src_offset === node.start~.

So the line is correct only when an instruction's ~src_offset~ equals the
~start~ the compiler recorded for the owning AST node.

** Root cause (in the clox compiler)
The compiler lives at
~/mnt/home/siobhan/Code/learn/cs/crafting-interpreters/clox~.  Every byte is
stamped at emit time with whatever token happens to be ~parser.previous~:

#+begin_src c
// src/lib/compiler.c
static void emitByte(uint8_t byte) {
  int srcOffset = (int)(parser.previous.start - getScannerStart());
  writeChunk(currentChunk(), byte, parser.previous.line, srcOffset);
}
#+end_src

clox is a single-pass Pratt compiler: an instruction for a construct is emitted
*after* the construct's children have been parsed.  By then ~parser.previous~
has advanced to the *last token consumed*, which is not the token the AST node
was anchored to.  Example from ~binary~:

#+begin_src c
static void binary(bool canAssign) {
  int start = parser.previous.start - getScannerStart(); // anchor = operator token
  parsePrecedence((Precedence)(rule->precedence + 1));    // consumes RIGHT operand
  expressionNode("Binary", start, 2);                     // node.start = operator offset
  ...
  case TOKEN_PLUS: emitByte(OP_ADD); break;               // src_offset = LAST token of RHS
}
#+end_src

For ~1 + 2~ the ~Binary~ node's ~start~ is the offset of ~+~, but ~OP_ADD~'s
~src_offset~ is the offset of ~2~.  They never match.

The same drift hits every instruction emitted after recursing into children:
~unary~, ~call~ (~OP_CALL~), ~dot~ (~OP_GET/SET_PROPERTY~, ~OP_INVOKE~),
assignment (~emitBytes(setOp, arg)~), logical ~and~/~or~ jumps, and the
statement-level jump/loop/pop instructions.  Only instructions emitted
*immediately* while ~parser.previous~ is still the right token line up today:
~number~, ~string~, and the ~literal~ keywords (true/false/nil).

~srcOffsets~ was built for clox's runtime needs (line numbers / error
reporting), where "most recently consumed token" is good enough.  The
visualizer is the first consumer that needs it to mean "the construct's anchor".

* Approach

Track an explicit *source anchor* in the compiler and stamp emitted bytes with
it instead of ~parser.previous.start~.  The anchor is the same offset each
parse function already computes and passes to ~expressionNode~ / ~createNode~,
so the instruction offsets are guaranteed to agree with the AST node offsets by
construction.

Mechanism: a module-level ~static int currentSrcOffset~ plus a setter; each
parse/statement function sets it immediately before emitting its own bytes.
Because emission is synchronous and children emit their bytes (with their own
anchors) before the parent emits, a single variable is sufficient — the
discipline is that a function must *re-set* the anchor after returning from a
child and before emitting its own instructions.  ~emitByte~ falls back to
~parser.previous.start~ when no anchor is set, preserving today's behaviour for
any site not yet migrated.

This is a compiler + WASM-rebuild change; the visualizer side is already wired
(the ~onClick~ handler in ~bytecode.ts~ has been uncommented).

Introduce a module-level anchor and route ~emitByte~ through it:

#+begin_src c
static int currentSrcOffset = -1; // -1 = "unset, fall back to parser.previous"

static void setSrcOffset(int offset) { currentSrcOffset = offset; }

static void emitByte(uint8_t byte) {
  int srcOffset = currentSrcOffset >= 0
      ? currentSrcOffset
      : (int)(parser.previous.start - getScannerStart());
  writeChunk(currentChunk(), byte, parser.previous.line, srcOffset);
}
#+end_src

Keep ~emitBytes~, ~emitLoop~, ~emitJump~, ~emitReturn~, ~emitConstant~ delegating
to ~emitByte~ (they inherit the anchor automatically).

The anchor must be *reset to ~-1~ between statements* (see the reset task), so
the fallback only ever fires for a genuinely unanchored emit rather than a
stale carry-over from a previous statement.  Every emitting site is expected to
set its own anchor; the fallback to ~parser.previous~ is a loud-failure safety
net, not the normal path.

* Formal parameters vs call-site arguments

** Diagnosis

There are two distinct "argument" concepts:

*** Call-site arguments (~f(1, a)~) — already wired
Each argument is compiled by ~argumentList()~ → ~innerExpression()~, which emits
the usual expression bytecode (~OP_CONSTANT~, ~OP_GET_GLOBAL~, …) with anchors
at each argument expression's own token.  The AST already has child nodes
(Number, Variable, …) with ~childType: Argument~ and matching ~start~ offsets.
These should connect once the src-offset anchoring work above is deployed.

*** Formal parameters (~fun f(a, b)~) — was broken
Parameter names in a function signature have *no dedicated binding bytecode* in
clox — arguments arrive on the stack when the function is ~OP_CALL~ed.  The only
instructions involving a parameter are ~OP_GET_LOCAL~ emitted when the parameter
is *read* in the body, and those were anchored to the *usage* token, not the
enclosing ~Function~ node.

The ~Function~ node already represents the whole declaration — name in
~attrs.name~, parameters in ~attrs.params~ (the ~(a, b)~ label), anchored at the
~fun~ keyword (~start~ from the ~open~ event).  Parameter reads should connect
there, not to separate child nodes or to per-usage ~Variable~ nodes in the body.

** Decision
Formal parameters are part of the ~Function~ / ~Method~ node, not separate AST
children.  ~OP_GET_LOCAL~ for a formal parameter anchors to ~current->srcOffset~
(the enclosing function's declaration offset — the ~fun~ keyword or method name),
so the connector lands on the ~Function~ node that owns ~attrs.params~.

* Decisions

** Implicit instructions are owned by the enclosing construct
Instructions with no natural single owning token — the implicit
~OP_NIL; OP_RETURN~ at the end of a function body, the ~OP_POP~ that discards a
condition, etc. — are anchored to the *enclosing construct's* offset (the
function name / keyword offset, the ~if~/~while~/~for~ keyword, ...).  They
should draw a connector to that construct's node rather than being left
unanchored.

** Per-operand offsets are a non-issue
A multi-byte instruction (e.g. ~OP_CONSTANT <index>~, jumps) writes a
~srcOffsets~ entry for *every* byte, so the operand bytes also carry an offset.
This does not matter: the disassembler only ever reads
~chunk->srcOffsets[offset]~ at each instruction's *opcode* offset (see the
~json*Instruction~ functions in ~debug.c~), never at an operand slot, so the
operand entries are dead data.  Having every byte inherit the opcode's anchor
via ~emitByte~ is exactly what we want; no special handling is needed.

** ~currentSrcOffset~ resets to ~-1~ between statements — fail loud
Reset the anchor to ~-1~ (unset) at the end of each statement.  A "forgot to
set the anchor" bug should surface immediately as a wrong/missing connector
rather than silently carrying a stale offset from a previous statement.
Failing loud is preferred over the more forgiving carry-over.

** ~srcOffsets~ has no other consumers — refactor freely
~srcOffsets~ exists solely to support this visualization feature.  It (along
with the JSON compiler logging and the ~emitByte~ change) was introduced in the
latest clox commit, ~fa3e8f4~ ("feat(lox-visualizer): Log compiler vm
instructions for visualization").  Nothing else reads it — runtime line numbers
come from a separate array — so any code from that commit can be refactored
without worrying about other consumers.
