#+date: 2026-06-18
#+TODO: TODO IN-PROGRESS | DONE

Make each line in the console/print pane *selectable* and draw a connector
between a printed result and the ~OP_PRINT~ instruction that produced it —
mirroring the existing lexer↔AST↔bytecode selection model.

Today the console is the one piece of the visualizer that sits *outside* the
store/connector architecture: it is rendered inline in the orchestrator
(~displayConsole~), its messages carry only ~text~, and clicking a line does
nothing.  This work promotes it to a real ~ConsolePanel~ and gives each printed
value the provenance it needs to join the shared selection model.

* Background

** How selection + connectors work today
The whole visualizer keys cross-panel selection on a single source byte offset,
~VisualizerSelection.selectedStart~ (~lox-data.ts~ 19–22).  Every selectable
artifact carries that offset:

- lexer spans → ~data-start~
- AST nodes → ~AstNode.start~ / ~data-start~
- bytecode rows → ~CompilerEvent.src_offset~ / ~data-src-offset~

A click writes ~{ selectedStart }~ to the selection store; each panel reacts in
~onSelectionChange~, highlights its matching element(s) and publishes a
connector *anchor* via ~setAnchor(rect | null)~.  The connector topology is
declared once in the orchestrator (~lox-visualizer.ts~ 80–81):

#+begin_src typescript
connectors.addLine('ast', 'lexer', colors.highlight);
connectors.addLine('ast', 'bc',    colors.highlight);
#+end_src

Panels never talk to each other — only through the store and the anchors.  See
~doc/todo/arch-refactor/00-overview.org~ for the full design.

** Why the join key already lines up for prints
After the ~print~-keyword anchoring done in
~doc/todo/instruction-ast-connector-fix.org~, the compiler stamps ~OP_PRINT~
with the offset of the ~print~ keyword (~compiler.c~ ~printStatement~ 1147–1152:
~setSrcOffset(start); emitByte(OP_PRINT)~).  That same value lands in the
disassembly as ~OP_PRINT~'s ~src_offset~ (~debug.c jsonSimpleInstruction~ reads
~chunk->srcOffsets[offset]~).  ~printStatement~ anchors *only* ~OP_PRINT~ to the
~print~ keyword (the value expression gets its own anchors), so a single
~src_offset~ identifies exactly the ~OP_PRINT~ row.

The catch: that offset only lives on the *static disassembly*.  The runtime
~print~ event the console consumes does not carry it.

** What the print event carries today (the gap)
~OP_PRINT~ executes in ~vm.c~ 435–439 and calls ~printValue(pop())~.  With
~JSON_LOG_PRINT~ defined, ~printValue~ (~value.c~ 81–90) emits:

#+begin_src json
{"msg_type": "print", "text": "..."}
#+end_src

~printValue~ is a *generic* value printer (also used by the GC and the
disassembler), so it has no access to the current chunk or instruction pointer
and *cannot* know the ~src_offset~.  The frontend mirrors this: ~PrintEvent~
(~events.ts~ 17–20) and ~ConsoleMessage~ (~state/state.ts~ 287–289) are
~{ text }~ only, the orchestrator pushes them with no offset
(~lox-visualizer.ts~ 98–104), and ~displayConsole~ (~lox-visualizer.ts~
209–218) renders inert ~<div>~s with no ~data-*~, no click handler, no anchor.

* Approach

Two halves:

1. *Provenance (C/WASM)* — emit the producing instruction's identity in the
   ~print~ event: ~src_offset~ (the join key), plus ~chunk~ + ~offset~ for an
   exact instruction match and future disambiguation.

2. *Frontend* — thread that offset through ~PrintEvent~ → ~ConsoleMessage~,
   promote the inline console to a ~ConsolePanel extends VisualizationPanel~
   (~panelId = 'console'~) that makes print lines clickable (writing
   ~selectedStart~) and reacts to selection (highlight + ~'console'~ anchor),
   then declare a ~console↔bc~ connector.

Because the console writes the *same* ~selectedStart~ the bytecode panel already
keys on, clicking a printed line lights up its ~OP_PRINT~ row *for free* (and,
via the existing ~ast↔bc~ / ~ast↔lexer~ lines, the ~Print~ AST node and source
tokens too — the whole chain).  No new selection field is required.

** Dependency
The core ~console↔OP_PRINT~ line works regardless of the connector-fix WASM
rebuild: both the print event's ~src_offset~ and the disassembly row's
~src_offset~ are read from the *same* ~chunk->srcOffsets[opOffset]~, so they
agree by construction.  The *extended* chain to the AST/lexer only lands on the
right ~Print~ node once ~instruction-ast-connector-fix.org~'s WASM rebuild is
deployed.  Ship this feature's WASM rebuild together with that one.

Move the JSON emission for prints out of the generic ~printValue~ and into the
~OP_PRINT~ case, where the frame, chunk and instruction pointer are in scope, so
the offset can be attached.  At the case body, ~frame->ip~ has already advanced
past the (single-byte) ~OP_PRINT~ opcode via ~READ_BYTE()~, so the opcode
offset is ~frame->ip - 1 - chunk.code~.

#+begin_src c
case OP_PRINT: {
#ifdef JSON_LOG_PRINT
  Chunk* chunk = &frame->closure->function->chunk;
  size_t opOffset = (size_t)(frame->ip - 1 - chunk->code);
  int srcOffset = chunk->srcOffsets[opOffset];
  const char* chunkName = frame->closure->function->name != NULL
      ? frame->closure->function->name->chars
      : "<script>";
  printf("{\"msg_type\": \"print\", \"text\": \"");
  printJsonValueText(pop());
  printf("\", \"chunk\": \"%s\", \"offset\": %zu, \"src_offset\": %d}",
         chunkName, opOffset, srcOffset);
#else
  printValue(pop());
  printf("\n");
#endif
  break;
}
#+end_src

Notes / sub-decisions:
- Use ~printJsonValueText~ (~value.c~) for the value text so the ~text~ field is
  JSON-safe (see ~Escape print text for valid JSON~).
- ~chunkName~ must match the disassembly's chunk label exactly — bare
  ~<script>~ / ~fn->name->chars~ (see ~debug.c~ 228 and ~vm.c~ 573), *not* the
  ~<fn ...>~ display form — so the frontend can match ~(chunk, offset)~ if it
  wants to.
- ~offset~ equals ~CompilerEvent.offset~ (the per-chunk byte offset of the
  opcode), and ~src_offset~ equals ~CompilerEvent.src_offset~.

*** Render: clickable print lines
Port ~displayConsole~ (~lox-visualizer.ts~ 209–218).  For each ~print~ message
that has a ~srcOffset~, set ~data-src-offset~, mark it clickable
(~cursor: pointer~), and on click write the store + stop propagation (so the
document-level deselect handler, ~lox-visualizer.ts~ 56–58, does not fire):

#+begin_src typescript
.attr('data-src-offset', d => d.type === 'print' && d.srcOffset != null ? d.srcOffset : null)
.classed('console-selectable', d => d.type === 'print' && d.srcOffset != null)
.on('click', (event, d) => {
    if (d.type !== 'print' || d.srcOffset == null) return;
    event.stopPropagation();
    this.selectionStore.set({ selectedStart: d.srcOffset, selectedAstNode: null });
});
#+end_src

Writing ~selectedAstNode: null~ follows the same protocol as the lexer/bytecode
panels — the AST panel resolves and writes the node back.

*** ~onSelectionChange~: highlight + anchor
Same structure as ~BytecodePanel.onSelectionChange~ (~bytecode-panel.ts~ 32–64):

1. Clear previous line highlight.
2. If ~selectedStart === null~ → ~setAnchor(null)~, return.
3. Find lines via ~querySelectorAll('[data-src-offset="N"]')~.  None → clear +

   ~setAnchor(lines[0].getBoundingClientRect())~ to feed the ~console↔bc~ line.

A loop body re-executes one ~OP_PRINT~, so several console lines can share one
~src_offset~ — highlight them all, anchor the first (see Decisions).

* Decisions

** Reuse ~selectedStart~ — no new selection field
The console joins the existing model on ~src_offset~ (the ~print~ keyword
offset).  This is the minimal change and gives the AST/lexer chain for free.
~chunk~ + ~offset~ are carried for an exact ~(chunk, offset)~ instruction match
and future disambiguation, but are not needed for v1 highlighting.

** Loop ambiguity is accepted for v1
A static ~OP_PRINT~ inside a loop produces N console lines that all share one
~src_offset~.  Selecting one line highlights the single producing instruction
(correct); selecting the instruction highlights all N lines and anchors the
connector to the first.  Per-execution precision (a unique connector per
iteration) would need a runtime execution index in the print event — e.g.
~(chunk, offset, executionCount)~ — and a richer selection key.  Deferred; note
it here so the ambiguity is a known, intentional limitation, not a bug.

** Provenance lives on the print event, not inferred
Matching console lines to instructions by program order or by text is
unreliable (conditionals/loops reorder execution vs. static layout; duplicate
values collide).  The offset is emitted from the VM at execution time, where it
is unambiguous.

** Console becomes a real panel
Promoting the inline console to ~ConsolePanel~ also closes the explicit TODO in
~doc/todo/arch-refactor/08-orchestrator-and-cleanup.org~ ("the console panel is
intentionally still handled inline … not yet a real panel") and the
~consoleMessages~-in-~LoxData~ open question in ~03-lox-data.org~.
