* Orchestrator's four responsibilities

Per ~doc/lox-visualizer-architecture.org~ → "The orchestrator":

1. Create the WASM instance and run source.
2. Accumulate WASM events into ~LoxState~ and, when aggregation completes,
   derive once and publish to the *data store* (~dataStore.set({ data })~).
3. Create the two stores (data + selection), the connector layer, and panels.
4. Handle the editor and re-run.

Everything else (selection state, cross-panel highlight, connector drawing) now
lives in panels + the connector layer.  Note: the orchestrator *publishes to
stores*; it does not call ~panel.onDataChange()~ directly — panels subscribe in
their base ~setUp~ (see 04).  The raw WASM event stream stays on ~d3.dispatch~
in ~lox-core~; the orchestrator is the bridge from that stream into the stores
(see ~00-overview.org~ → "State management").

#+begin_src typescript
render() {
    // reset selection first so panels clear highlights/anchors in the same pass
    this.selection.set({ selectedStart: null, selectedAstNode: null });
    // derive the whole snapshot and publish in one shot (no incremental writes)
    this.dataStore.set({ data: deriveLoxData(this.loxState) });       // 03
    this.displayConsole();
}
#+end_src

This is the "set all the events when done aggregating" model: accumulation
happens in the ~lox.events.on(...)~ handlers; the single ~dataStore.set~ fires
only when a run has finished aggregating.

~requestAnimationFrame(render)~ and parser ~PROGRAM close~ ⇒
~requestAnimationFrame(render)~ flags (~rendered~, ~parserRendered~; demo 84–111)
stay in the orchestrator.
